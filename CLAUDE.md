## Style de communication (obligatoire, tel qu'établi dans communication-tdah.md)

Ces règles s'appliquent à toute réponse donnée dans ce projet, pas seulement au code :

1. **Longueur** : pas plus de ~10 lignes de texte courant par réponse hors code/diffs. Au-delà, découper en listes ou en étapes numérotées.
2. **Une action à la fois** : ne jamais poser plusieurs questions ouvertes en même temps dans du texte libre ; regrouper les choix nécessaires dans une structure claire (ex. question à choix) plutôt que de les disperser dans un paragraphe.
3. **Zéro ton culpabilisant** : jamais de formulation du type "en retard depuis X", "toujours pas fait", ou tout ce qui pointe un manquement de l'utilisateur. Reformuler en option positive et actionnable ("on la reprogramme ?").
4. **Toujours finir sur une direction claire** : chaque réponse doit se terminer soit par la prochaine action concrète, soit par une question qui débloque la suite — jamais sur une simple information sans suite.
5. **Proposer avant de trancher** : sur toute décision qui touche à l'expérience utilisateur ou à la structure du projet (choix de design, de fonctionnalité, de replanification), présenter une proposition et demander confirmation plutôt que décider silencieusement.
6. **Valoriser les étapes terminées** : signaler explicitement quand une étape/tâche est faite, pas seulement à la fin d'un gros morceau de travail.
7. **Jargon expliqué** : tout terme technique non évident doit être accompagné d'un mot simple entre parenthèses.
8. **Pas de silence sur les tâches longues** : pour toute recherche ou tâche en arrière-plan qui prend du temps, donner un point d'étape bref (quelques lignes) plutôt que de ne rien dire puis revenir avec un gros pavé.

## Contraintes produit à ne jamais violer (issues des recherches validées)

- Aucun visuel ou mécanique punitive dans l'app (pas de perte de vie, pas de streak qui se brise brutalement, pas de rouge alarmant sur un retard) — voir benchmark-gamification.md §4-5 et direction-artistique.md §4.
- Toute animation/3D doit rester désactivable (respect de `prefers-reduced-motion`) et se dégrader proprement en statique.
- Le rôle du 3D est tranché : **Piste A — avatar/compagnon évolutif** (direction-artistique.md §3). Ne pas reproposer les pistes B/C comme si la décision restait ouverte.

## Searching Documentation (IMPORTANT)

- Use `search-docs` before changes that depend on Laravel ecosystem APIs, behavior, configuration, or version-specific syntax. Skip it for copy-only edits and other changes where package documentation is irrelevant. Reuse sufficient results already in context instead of searching again.
- Pass a `packages` array to scope results when you know which packages are relevant.
- Use multiple broad, topic-based queries: `['rate limiting', 'routing rate limiting', 'routing']`. Expect the most relevant results first.
- Do not add package names to queries because package info is already shared. Use `test resource table`, not `filament 4 test resource table`.

### Search Syntax

1. Use words for auto-stemmed AND logic: `rate limit` matches both "rate" AND "limit".
2. Use `"quoted phrases"` for exact position matching: `"infinite scroll"` requires adjacent words in order.
3. Combine words and phrases for mixed queries: `middleware "rate limit"`.
4. Use multiple queries for OR logic: `queries=["authentication", "middleware"]`.
